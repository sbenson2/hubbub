# Invites and several servers: implementation plan

**Goal.** Replace hand-made community files with Discord's flow:
- The rail's "+" creates a server; you sit in it alone until friends arrive.
- "Invite People" gives a `hubbub://join/…` link (and its QR) to copy and send.
- Friends paste or click the link and are admitted by any online member.
- One app can be in several servers at once.

**Design:** `docs/superpowers/specs/2026-10-17-invites-design.md`, approved by the owner on 2026-10-17. Executors read it first.

**Execution:**
- Use `subagent-driven-development` with a ledger at `.superpowers/sdd/2026-10-17-invites/progress.md`.
- Spike 1 (`2026-10-17-spike-1-rotating-host-calls.md`) is paused at the T8c fix round. It resumes after Task 14.

- **Usage budget (`~/.agents/AGENTS.md`):**
  - One heavy agent at a time.
  - A subagent runs only commands that finish within 4 minutes.
  - The main session runs these in the background:
    - the first Windows `cargo test` (cold compile);
    - `flutter build windows --release` (about 4 minutes cold, 40 s warm);
    - Mac builds;
    - two-machine runs.
  - Each agent stays under 300k context.
- **Tests:**
  - Core tests are hermetic, using `RelayChoice::Disabled` and iroh `MemoryLookup`. The baseline must stay green: `cargo test -p hubbub-core --features test-util` gives lib 77 passed and 4 ignored, handover 10, text 5. `flutter test` gives +34 on Windows.
  - After each UI task, the controller shows the owner the real running app with a screenshot.
- **No new crates for signing.** iroh 1.3.0 re-exports `SecretKey::sign`, `PublicKey::verify` and `Signature`.
- **New pub packages need the exact versions approved by the owner:** `app_links 7.2.2` and `qr_flutter 4.1.0`.
- **Out of scope:** kicking or bans, roles beyond owner, renames, deleting a server for everyone, MLS, recovery codes, device linking, avatars other than initials, and phone builds.

## Task 1: Community state v2 and signed members
**Files:** `core/src/community.rs` (rewrite), `core/src/ids.rs` (add a `CommunityId` of 16 bytes as hex).

**Interfaces:**
- `CommunityState`:
  - `id: CommunityId`, `name: String`, `owner: MemberId`, `secret_hex`, `channels: Channels`, `revoked: BTreeSet<InviteId>`, `members: BTreeMap<MemberId, MemberEntry>`.
  - `MemberEntry { id, name, can_host, door: MemberId, via_invite: Option<InviteId>, admitted_by: MemberId, sig: Signature }`.
- `CommunityState::create(name, &Identity, can_host)` makes an owner entry that signs itself.
- `admit(&mut self, &Identity, entry)` signs a new entry as the admitter.
- `verify_entry(&entry)` checks the chain: the admitter must be a verified member, and the owner signs itself.
- `merge(&mut self, other) -> bool` is a union by ID. On a conflicting entry it keeps the lowest `(admitted_by, sig)` bytes. It rejects a state whose id or owner differs.
- `public_view()` returns the state without `secret_hex`, for `StateSync`.
- `save_atomic(path)` writes a temp file, then renames it.
- `e2ee_key()`, `text_key()` and `channels()` behave as before.

**Tests (unit):**
- the owner self-signature verifies;
- a forged admitter or a tampered name is rejected;
- merging A∪B equals B∪A and is idempotent;
- an owner or id mismatch is refused;
- a 150-member `public_view()` serialized as a `CtlMsg` stays under the 64 KiB frame limit (`proto.rs:12`);
- an atomic save that is interrupted leaves the old file intact.

**Verify:** `cargo test -p hubbub-core --lib`.

## Task 2: Invite link codec
**Files:** new `core/src/invite.rs`.

**Interfaces:**
- `Invite { v: u8, cid, invite_id: [u8; 8], expires_min: u32 (0 = never), max_uses: u8 (0 = unlimited), name (≤24 UTF-8 bytes, truncated on a char boundary), doors: Vec<MemberId> (1..=3, inviter first), inviter: MemberId, sig }`.
- `Invite::create(&Identity, &CommunityState, expires, max_uses, doors) -> Invite`.
- `to_link() -> String` produces `hubbub://join/<base64url-no-pad>`.
- `parse(text) -> Result<Invite>` finds the first `hubbub://join/` case-insensitively and ignores surrounding text, whitespace, line breaks and trailing `.,)>`. It also accepts the bare code.
- `verify(&CommunityState) -> Result<(), Deny>`. `Deny` is one of `Expired`, `Revoked`, `UsedUp`, `UnknownInviter` or `BadSignature`.

**Tests:**
- a round-trip;
- one flipped byte gives `BadSignature`;
- a link with 3 doors and a 24-byte name is ≤ 310 characters;
- a link pasted inside an SMS sentence still parses;
- expiry boundaries;
- `UsedUp` counts the entries whose `via_invite` matches.

**Verify:** `cargo test -p hubbub-core --lib`.

## Task 3: Live membership in the node
**Files:**
- `core/src/node.rs` (frozen-community uses at `:145,151,225,270,453,468,924`; `Inner.community` `:391`; dial loops `:201`; `read_loop` `:671`);
- `core/src/net.rs` (accept check at `:150`);
- `core/src/proto.rs` (ALPN v1, new messages);
- the helpers in `core/tests/handover.rs` and `core/tests/text.rs`.

**Interfaces:**
- A `tokio::sync::watch<Arc<CommunityState>>` held by the node: readers use `borrow()`, and a change spawns dial loops for new members.
- `CtlMsg::StateSync { state }` is sent after `Hello` and on every change. The receiver merges, saves if anything changed, and emits `NodeEvent::MembersChanged`.
- `Node::members()` and `member_name` read the live state. The node gets `admit()`, the hook used in Task 6.
- ALPNs become `hubbub/ctl/1` and `hubbub/lk-signal/1`. Task 4 adds the per-server suffix.

**Tests:** new `core/tests/membership.rs`:
- a member admitted at runtime on node A is dialed by A and connects to B without a restart;
- three nodes converge on the same member set after concurrent admissions;
- `MembersChanged` fires once per real change.

The existing handover and text suites pass with signed v2 state.

**Verify:** `cargo test -p hubbub-core --features test-util`. The first Windows run is a cold compile, so the controller runs it in the background.

## Task 4: Hub, one endpoint for every server
**Files:** new `core/src/hub.rs`; split `core/src/net.rs` into the hub-owned endpoint and accept loop plus a per-community view; `core/src/lib.rs`.

**Interfaces:**
- `Hub::open(root, HubConfig { can_host, relay, livekit_bin })`:
  - takes `<root>/hub.lock` via `File::try_lock`, and fails clearly if another process holds it;
  - loads `identity.key` and `profile.json { name }`;
  - starts a `Node` for each `communities/<cid>/community.json`.
- `Hub::create_community(name)`, `communities()`, `node(cid)`, `leave(cid)` (stops the node, removes its ALPN, archives the folder), and `shutdown()`.
- The ALPN pair per server is `hubbub/ctl/1/<cid-hex>` and `hubbub/sig/1/<cid-hex>`, applied with `Endpoint::set_alpns` (iroh 1.3.0 `endpoint.rs:984`) whenever the set changes. The accept loop routes by ALPN to that server's live membership check.
- `Node::shutdown` closes only its own connections, never the endpoint (`node.rs:311`).

**Tests** (with `MemoryLookup`):
- two hubs share two servers and each server's text stays separate;
- a third hub that's in only one server gets ALPN refusal for the other;
- after `leave`, the server's ALPN is refused;
- a second `Hub::open` on the same root fails.

**Verify:** `cargo test -p hubbub-core --features test-util`.

## Task 6: The door and the join protocol
**Files:** new `core/src/join.rs`; `hub.rs`.

**Interfaces:**
- **The door:** a second endpoint whose key is derived from the identity with HKDF (`hubbub door v1`). It is built with `clear_ip_transports()` (`endpoint.rs:510`), so it's relay-only and strangers never learn a member's IP. It accepts only `hubbub/join/1`, and is rate-limited globally (e.g. 10 per minute).
- **Messages:**
  - `JoinRequest { cid, invite, name, can_host }`;
  - `JoinAccepted { state }` (with the secret; the transport is QUIC/TLS keyed by ID);
  - `JoinDenied { reason }`;
  - `Rejoin { entry chain }`, used on the main endpoint when a member doesn't yet know the joiner.
- **The member side:**
  1. verify the invite against its own state;
  2. `admit`;
  3. broadcast `StateSync` *before* replying;
  4. reply.
- An existing member is simply accepted again and uses nothing up.
- **The joiner side:** `Hub::join(link, events)` tries the doors staggered at 0, 1.5 and 3 s, then keeps retrying. It emits `Trying`, `Offline` (no door answered within a cycle), `Denied(reason)` or `Joined(cid)`. It can be cancelled. On `Joined` it saves the state and starts the node.

**Tests:**
- an accepted join, after which the new member texts the others;
- expired, revoked, used-up and unknown-inviter are each denied;
- an existing member re-joins;
- the doors are offline, then one comes online and the join completes;
- `Rejoin`: Bob is admitted while Carol is offline, Carol comes back, and Bob and Carol connect without a third member;
- two members admit the same joiner and the states converge.

**Verify:** `cargo test -p hubbub-core --features test-util`.
